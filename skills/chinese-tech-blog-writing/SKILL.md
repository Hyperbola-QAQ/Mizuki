# 中文技术博客写作

写出能让目标读者理解判断依据、复现实操并安全地应用到自己环境的中文技术文章。默认采用务实、清晰、带有实践感的语气；以已验证的环境和结果为中心，不把猜测包装成结论。

## 个人博客默认格式

为用户的个人博客创建文章时，在正文前固定使用以下 Frontmatter；根据文章内容替换尖括号中的值。`series` 仅在文章属于连续主题时保留。

```yaml
---
title: <对象 + 场景 + 任务或结果>
published: YYYY-MM-DD
updated: YYYY-MM-DD
pinned: false
description: <一句话说明环境、目标和覆盖范围>
tags: [<技术对象>, <技术对象>]
category: <分类>
author: Hyperbola
draft: false
series: <可选的连续主题>
---
```

- `published` 与 `updated` 使用实际日期；需要准确时刻时可使用带时区的 ISO 时间戳。
- 文章正文中的所有标题均使用一级标题 `#`，包括“前言”“环境准备”“操作步骤”“验证”“总结”等。不要使用 `##`、`###` 等更低级标题；同一章节内的层次改用加粗小标题、编号列表或项目列表表达。

## 先确定文章类型

- 教程、部署或配置文章：按“目标与适用范围 → 前提与环境 → 分阶段操作 → 验证 → 注意事项/常见问题 → 总结”组织。
- 故障排查或复盘文章：按“现象与影响范围 → 已知条件 → 假设 → 最小化验证或对照实验 → 根因 → 修复 → 影响、取舍与复盘”组织。
- 经验分享：先交代背景和决策约束，再给出方案、结果与适用边界。

不必机械套用全部章节；保留能帮助读者完成任务和理解取舍的部分。

## 踩坑过程必须复盘

只要文章涉及踩坑、失败尝试、版本差异或非直观限制，就必须详细写出过程，不能只保留最终可用配置或一句“注意避坑”。按实际情况交代：

1. **触发条件**：环境、版本、前置配置和具体操作；说明问题在什么范围内出现。
2. **现象与证据**：错误信息、异常行为、关键日志、命令输出或可观察的结果。不要伪造输出；敏感信息必须脱敏。
3. **排查与无效尝试**：按时间或逻辑顺序说明做过什么、为何尝试、结果如何，以及该结果排除了或确认了什么。无效尝试也应保留，只省略与结论无关的重复试验。
4. **根因与修复**：区分已证实的根因和合理推断；给出最终修改、验证结果及其生效原因。
5. **避坑结论**：总结触发信号、适用边界、风险、替代方案和下一次可直接采用的检查或操作。

若没有真实踩坑，不要为了套结构而编造；可省略本节。

## 写作方式

- 标题交代技术对象、场景和任务或结果，例如“使用 X 部署 Y”或“X 场景下 Y 的排障实战”。摘要用一句话说明环境、目标和覆盖范围。
- 开头提供影响结论、环境版本、关键角色、拓扑或前置条件；只保留后文会用到的信息。
- 以操作决策而非命令罗列为线索。每个关键步骤说明：为什么现在做、执行什么、预期看到什么，以及结果代表什么。
- 使用直接、自然的中文；保留必要的英文技术术语、命令、路径、版本、端口、地址、配置键，并用反引号标记。
- 用短段落、编号步骤和列表组织密集信息。用粗体突出关键现象、结论、参数或风险，但不要整段加粗。
- 明确区分观察、推断与结论。不能确认的内容标为“待验证”“可能”或给出验证方法；不要虚构日志、性能数据、兼容性或根因。
- 对临时方案与长期方案分别说明适用条件和代价，例如可用性、隔离、性能、安全性或维护成本。
- 以“总结”“经验小结”或“一句话总结”收束，提炼可迁移的判断方法，而不只是重复步骤。

## 技术材料

- 命令、配置、输出和拓扑都用代码块，并使用准确的语言标识，如 `bash`、`yaml`、`toml`、`ini`、`sql`、`text`、`mermaid`。配置片段只展示当前步骤相关的最小内容；较长的完整配置放附录并脱敏。
- 命令前说明其目的；命令后给出应该检查的状态、输出或行为。多主机/集群内容要标注执行节点、角色和依赖关系。
- 用 ASCII 图或 Mermaid 呈现链路、流量或组件关系时，只画支撑当前判断的关键路径。
- 插图的 alt 文本描述信息本身。需要对比的图片或配置，配上简短说明，让读者理解比较维度。
- 引用外部资料只用于支撑事实、版本差异或命令依据；链接到原始、可信来源。

## 安全与可操作性

- 绝不公开密码、Token、私钥、真实账号、敏感内网地址、完整生产拓扑或个人信息。示例必须脱敏，必要时使用明确占位符。
- 涉及删除、覆盖配置、重启、网络切换、权限提升、暴露端口或数据迁移时，写明作用范围、前提、风险、验证点与回滚/恢复路径。
- 不鼓励读者在不了解影响时复制粘贴破坏性命令。区分“示例”“需要替换的值”和“可直接执行的命令”。
- 发布前核对标题与摘要、代码块闭合、命令可读性、链接和图片、示例脱敏、步骤顺序，以及结论是否由文中的证据支持。

## 与目标平台协作

先读取目标博客或文档系统的写作指南、Frontmatter schema 和 Markdown 扩展；这些项目规则优先于本 Skill。根据平台要求补全元数据、资源路径、内部链接和构建检查，但不要擅自变更站点配置或发布文章。
